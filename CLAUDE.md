# Compile & Conquer (iOS)

A coding game: you write real Python to control machines (a farm drone, a warehouse forklift…)
across generated levels. Campaigns are per programming language; Python is first.

## Build & release rules (do not break)
- The project is generated by XcodeGen from `project.yml`; there is no checked-in `.xcodeproj`.
- CI (`.github/workflows/build.yml`) builds an unsigned IPA on every push to `main` that touches the app.
- **Versions are stamped by CI only**: app version `0.2.<run_number>`, build `<run_number>`.
  Never hardcode a version in `project.yml` or Info.plist; CI verifies the IPA's version and fails otherwise.
- Release tag is `v<version>` and the asset is `CompileConquer-<version>.ipa`. The user's Mango Signer
  reads the version from the tag (minus the `v`) and groups apps by the IPA file name with digits removed,
  so keep both formats exactly like this. Versions must only ever go up.
- Bundle ID `com.mangomods.compileconquer` must never change (it would become a separate app).
- Big changes go on a side branch (tests run there, no release is cut), then merge to `main` once.

## Tests and screenshots (how to see the game)
- `.github/workflows/tests.yml` runs on `main` and `rework` in the iOS simulator:
  - `Tests/SmokeTests.swift`: every level generates, opens, has a 3-star limit, is beaten by a general
    Python solver, and its *taught* solution (`TestSupport/PySolutions.swift`) earns 3 stars on many seeds.
  - `UITests/FlowTests.swift`: taps through the real app and saves screenshots to `/tmp/cc-shots`,
    which CI force-pushes to the `ci-screenshots` branch. Fetch that branch to look at the game:
    `git fetch origin ci-screenshots && git archive FETCH_HEAD | tar -x -C <dir>` (images are sideways; rotate 90°).
- UI-test launch arguments: `-uitest.allStars N`, `-uitest.noIntro YES`,
  `-uitest.code.<level id> <base64 python>`, `-owner.anyCampaign YES`, `-set.speed N`.
- There is no Swift toolchain in the dev container: CI is the compiler. Add a test when adding a level.

## Design direction (from the owner)
- Difficulty ramps inside every language campaign: each one starts gentle at the Farm, and every
  world after it and every level within a world gets progressively harder. Languages are not ranked.
- Every world is a different place with its own machine, mechanics, commands and setup code;
  only the language is shared. The Farm is the only drone/crops world. Planned next:
  Mars Mine (rover: battery, drilling, charging pads), Deep Ocean (sub: sonar, oxygen), Rail Yard (switches, timing).
- Every level's main.py starts with a **locked setup** that declares every variable and defines every
  command with its real body (`Core/FarmSetup.swift`, `Core/Warehouse/WarehouseSetup.swift`).
  Keep those bodies in sync with the world structs. Starter code and briefs point at the setup and at
  the idea being taught; they never just give the answer. Setup lines stay ≤ 46 characters (tested).
- Shortcuts like reusing one soil tile are allowed on the Farm and the first Warehouse levels. Later
  levels may close them off, but only through rules written visibly in that world's setup code
  (example: `MAX_LOST` on "Pick of the Crop").
- Stars are about ticks. The 3★ limit is computed per generated map so the solution a level teaches
  always earns 3 stars (`ParStyle`, `parSlack`; enforced by `testIntendedSolutionsEarnThreeStars`).
  The Farm is forgiving; later worlds can be tighter. The Tidy bonus (lines of code) is separate.
- Maps: a level keeps its map (seed) until it's beaten or "New map" is tapped; levels marked
  re-roll change part of the map on every Run so code can't memorize it.
- Planned: a free currency (Bits) and a paid one (Cores, later), both cosmetic-only. Ideas live in
  `docs/IDEAS.md`; add new ideas there as they come up, don't build them until the owner picks them.

## How a run works
- `Core/Python/` is our own Python subset (lexer, parser, tree-walking interpreter): variables,
  if/elif/else, while, for, def/return, lists, dicts, tuples, slices, list comprehensions, f-strings,
  print and common builtins. No imports or classes. Errors are written for beginners (did-you-mean,
  locked-command messages).
- Pressing Run simulates the whole program off the main thread (`Core/Runtime/Simulator.swift`)
  against a copy of the world, recording a trace of ticks, prints and variable snapshots.
  `Game/GameSession.swift` plays the trace back, and can pause, step, step back and scrub.
- Each world installs its own builtins (commands + read-only objects like `drone`, `field`,
  `loader`, `floor`, `BAYS`) in `Simulator.swift`. They must match that world's locked setup code.
- The player's code is capped at 5000 lines; the editor measures its own content height.

## Code layout
- `CompileConquer/Core` – pure game logic: `FarmWorld`, `Levels` (LevelSpec + Farm chapter + generator),
  `ParSolver`, `FarmSetup`, `Warehouse/`, `Python/`, `Runtime/`, `GameProgress` (stars, Tidy, saved code/seeds).
- `CompileConquer/Game` – level screen (`GameScreen`, `GameHUD`, `ResultViews`, `HandbookView`),
  `GameSession`, the SpriteKit scenes and code-drawn art, `CodeEditor` (autocomplete, key row).
- `CompileConquer/Menus` – title (live demo), worlds, level map, settings, `WorldArt` thumbnails.
- `CompileConquer/App` – `Theme`, `AppSettings`, `SoundFX` (all audio is synthesized at launch).
- Landscape only, iOS 17+, Swift 5 mode, SwiftUI + SpriteKit, no external packages, no asset files
  besides the app icon.

## Settings & owner tools
- Settings: sound/music, code text size, starting speed, map coordinates, crop age tags, haptics, reset.
- Owner tools: tap the version 7 times in Settings, enter the owner code (starts as "conquer").
  "Play any campaign" opens every built campaign/world; levels still unlock in order.
